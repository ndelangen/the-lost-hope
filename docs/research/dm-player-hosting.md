# DM hosting and the player archive

Verified against the repository's `main` commit on 12 November 2026 and Netlify's documentation. The production homepage returned HTTP 200 without credentials. The site's current Netlify plan and visitor-access settings require a dashboard check.

## What the player site publishes

The current build takes campaign registries as input, prerenders the public route list, and publishes `dist/client`. Its outputs include HTML, browser code, images, social previews, page metadata, structured data, and the sitemap. The current build audit checks that these artifacts exist and match the public page contract. A player access policy would also need to check which records and fields enter the build. [Build configuration](https://github.com/ndelangen/the-lost-hope/blob/4ebf2cdfb3bfba892a8a3451ac1720f49ede7fee/netlify.toml) · [Prerender configuration](https://github.com/ndelangen/the-lost-hope/blob/4ebf2cdfb3bfba892a8a3451ac1720f49ede7fee/vite.config.ts#L45-L62) · [Public build audit](https://github.com/ndelangen/the-lost-hope/blob/4ebf2cdfb3bfba892a8a3451ac1720f49ede7fee/scripts/audit-public-build.ts#L33-L96)

GitHub reports the repository as public. Restricting Netlify visitors controls access to the deployed site. Private source records, assets, and handover notes need storage outside the public Git tree, history, and issue tracker. Material that previously shipped also needs its own review. Publishing a replacement leaves older Netlify deploys with distinct URLs. Netlify documents deletion for eligible old deploys, after which their permalinks return 404. Copies made while material was public can persist. [Netlify deploy history and deletion](https://docs.netlify.com/deploy/manage-deploys/manage-deploys-overview/)

## What Netlify can enforce

- **Whole project.** Netlify documents private project visibility with a Netlify team login and a plan-dependent shared password. Protection can cover production, Deploy Previews, and branch deploys. On credit-based Free and Personal, private access is owner-only and the shared password setting is unavailable. Check the actual project plan and selected scope before counting on either feature. Preview and branch URLs can otherwise be shared, and `noindex` controls discovery only. [Project visibility](https://docs.netlify.com/manage/security/secure-access-to-sites/project-visibility/) · [Password protection](https://docs.netlify.com/manage/security/secure-access-to-sites/password-protection/) · [Preview URL visibility](https://docs.netlify.com/deploy/deploy-overview/#preview-url-visibility)
- **Specific routes and data.** Netlify supports role-based routing with signed identity tokens, and functions and edge functions can check roles on requests. A shared deployment can keep a public static archive while serving private material through authorized handlers. The public publish directory should contain public data only. A login prompt in React or a guard on one application route leaves independently served artifacts available. Netlify's request chain includes separate function, rewrite, and static file handling, and a static rewrite can skip an edge function attached only to its target. [Role-based access control](https://docs.netlify.com/manage/security/secure-access-to-sites/role-based-access-control/) · [Identity in functions](https://docs.netlify.com/manage/security/secure-access-to-sites/identity/use-identity-in-functions/) · [Request chain](https://docs.netlify.com/resources/troubleshooting/request-chain/) · [Rewrite caveats](https://docs.netlify.com/build/edge-functions/declarations/#processing-order-caveats)
- **URLs and caching.** Treat the production URL, preview URL, branch URL, and available deploy permalinks as distinct checks. For authenticated data, keep shared CDN caching disabled unless a verified cache policy preserves the audience boundary. Check direct media and page URLs as well as login, authorization, and mutation routes. [Deploy overview](https://docs.netlify.com/deploy/deploy-overview/) · [Caching behavior](https://docs.netlify.com/build/caching/caching-overview/)

## What each option implies

| Option | Player archive | DM workspace |
| --- | --- | --- |
| Local DM workspace | Keep the current player deployment and build it from approved material. | Run on the DM's machine with private local storage and backups. No second hosted project is required. |
| Separate hosted DM deployment | Keep the current player deployment and build it from approved material. | Use a separate Netlify project with private source and assets and protection across its deploys. Verify access from a signed-out browser on each URL class. Shared schema and UI code can still live in one codebase. |
| Shared deployment with server-side sign-in | Keep static delivery for public routes and assets. If party-only or individual-player views are needed, deliver them through authorization-aware routes. | Load private records and media through authorized handlers outside the public publish directory. Verify that metadata, build output, and unauthenticated requests contain public material only. |

For one DM already using local dev at the table, the local option has the fewest deployment changes. It depends on the player build receiving an explicit public projection and on private data staying out of public source and artifacts. A hosted option earns its extra access and deployment work if the DM needs remote access, or if the chosen player experience needs authenticated material or live updates. That product choice stays with the parent map.
